# 因果诊断能力

当你已经能跑实验、改训练脚本、修 policy / dataset / workspace 里的 bug 之后，下一步最重要的能力之一就是：

> **结果变了，到底是谁导致的？**

这就是因果诊断能力。

---

## 1. 为什么这项能力重要

一个实验结果变化，可能来自很多层：

- 数据变了
- 动作表示变了
- loss 变了
- 优化器更新节奏变了
- dataloader / batch sampler 变了
- 评测脚本读错 ckpt 了
- 甚至只是 profile 改了 batch size

如果不能把这些因素分开，你就会出现两种典型问题：

1. 把工程问题误判成方法问题
2. 把方法提升误判成训练技巧带来的假提升

---

## 2. 一组实验结果应该从哪几层解释

建议固定按下面 5 层去排查：

### 2.1 数据层

- 原始数据分布是否偏？
- data amount 是否足够？
- task 是否太难或太简单？

### 2.2 表示层

- action space 是否让学习更难？
- observation 到 action 的映射是否条件不好？

### 2.3 优化层

- batch / grad accumulation / lr / scheduler 是否改变了优化行为？
- auxiliary loss 的 scale 是否合适？

### 2.4 实现层

- dataset / sampler / dataloader 是否对齐？
- EMA / optimizer step 是否和 accumulation 一致？
- train 和 eval 的输入输出接口是否一致？

### 2.5 评测层

- 评测读的是不是同一个 setting 的 ckpt？
- clean / randomized 是否混淆？
- 成功率指标是否能代表真正关心的能力？

---

## 3. 现在最值得练的动作

### 3.1 每次异常都做“分层归因”

比如出现 OOM，不要只记“显存炸了”，而要写：

- 是 batch 导致的？
- 是 backbone 导致的？
- 是 val batch 和 train batch 不一致？
- 是梯度累积没真的在起作用？

### 3.2 每次效果变化都做“候选解释列表”

例如 geoaux 成功率上升时，不要只写“方法有效”，而要同时写：

- 解释 A：几何辅助真的改善了 learnability
- 解释 B：额外辅助 loss 带来了 regularization
- 解释 C：profile 改动导致训练更稳

### 3.3 固定使用最小对照原则

一个结果要有说服力，至少要知道：

- 控制项是什么
- 唯一变化的变量是什么
- 如果没控制住，会污染什么结论

---

## 4. 一个实用的判断模板

以后每次结果变化，都可以按这四句写：

1. **现象**：我观察到什么变化
2. **候选解释**：至少列两个
3. **反例检查**：有没有别的工程因素也能解释这个现象
4. **最小对照实验**：如何把它们区分开

---

## 5. 这项能力真正练出来的标志

当你以后看到一个结果时，第一反应不再是：

- 这个方法厉害
- 这个方法不行

而是：

> 这个现象最可能来自哪一层？
> 我现在有足够证据把别的解释排掉吗？

这就说明因果诊断能力开始形成了。
